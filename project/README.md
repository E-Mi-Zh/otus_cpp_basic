# WayStation

WayStation - программа для подъёмв клиент-серверного IP-туннеля под Linux. Клиент
создаёт виртуальный интерфейс TUN и забирает с него IPv4-пакеты. Каждый пакет он
пропускает через выбранный кодек и отправляет серверу по TCP. Сервер снимает
обёртку и возвращает пакет ядру через свой TUN, а ядро уже решает, что с ним
делать дальше - например, отправить в интернет.

Код написан на C++17, для сети используются обычные блокирующие POSIX-сокеты. В
дальнейшем планируется замена на что-то более кросс-платформенное и в духе С++,
например, на Boost Asio.

Клиент и сервер - одна и та же программа, запущенная в разных режимах. Сборка и
запуск проверялись на Linux. Все три кодека собраны в один бинарник, нужный
выбирается ключом `--plugin`. `identity` передаёт кадр без изменений (нужен для
отладки), `padding` добавляет случайные байты перед кадром, `irc` - передаёт кадр
как сообщение IRC/

## Архитектура

В основе лежит конвейер. Операционная система кладёт IPv4-пакет в TUN, программа
заворачивает его в кадр, а кодек превращает кадр в байты для TCP. На другой
стороне всё происходит в обратном порядке, и пакет возвращается в ядро.

```text
                                     интернет, уровень 2
                                              |
                                              ^
клиент, пространство wsc        сервер, хост
+--------------------------+    +-------------+------------+
| ОС: ping и маршруты      |    | ОС: маршруты и NAT       |
|             |            |    |             ^            |
|             v            |    |             |            |
| TUN ws1  10.0.0.2/24     |    | TUN ws0  10.0.0.1/24     |
|             |            |    |             ^            |
|             v            |    |             |            |
| кадр, затем кодек        |    | кодек, затем кадр        |
|             |            |    |             ^            |
|             v            |    |             |            |
| veth-c  10.200.0.2/24    |    | veth-h  10.200.0.1/24    |
+-------------+------------+    +-------------+------------+
              |                               ^
              +---------- TCP 9000 -----------+
```

Подсетей две: в `10.0.0.0/24` находятся
адреса туннеля, а по `10.200.0.0/24` идёт сам TCP. Если объединить их в одну,
ядро начнёт отправлять пакеты туннеля внутрь самого туннеля.

### Модули

Обо всех частях программы знает только `main`: он разбирает аргументы, создаёт
остальные модули и связывает их между собой. Сами модули о соседях ничего не
знают, поэтому каждый можно написать и проверить отдельно.

```text
           +----------------------------+
           | main                       |
           | argv, потоки, счётчики     |
           +----------------------------+
        |                 |                 |
        v                 v                 v
+--------------+  +--------------+  +--------------+
| tun_device   |  | tcp_link     |  | i_codec      |
| /dev/net/tun |  | один TCP     |  | identity     |
| read, write  |  | send, recv   |  | padding, irc |
+--------------+  +--------------+  +--------------+
                                            |
                                            v
                                   +----------------+
                                   | frame_parser   |
                                   | внутри кодека  |
                                   +----------------+
```

Обязанности распределены так:

- `tun_device` открывает `/dev/net/tun`, назначает интерфейсу адрес и поднимает
  его, а дальше просто читает и пишет сырые IPv4-пакеты. О кадрах, кодеках и TCP
  он не знает.
- `tcp_link` устанавливает одно соединение и передаёт по нему байты. Внутри
  `send_all` крутится цикл: один вызов `send` вправе отправить только часть
  буфера, поэтому остаток досылается, пока не уйдёт всё.
- `frame_parser` собирает целые кадры из потока, который приходит кусками
  произвольного размера. Откуда взялись эти куски, ему неважно.
- `i_codec` переводит кадр в байты для провода и обратно. Парсер кадров
  находится внутри кодека: сначала кодек снимает свою обёртку, и только потом
  парсер ищет границы кадров.

### Слои на проводе

Самый внешний слой - TCP. На сегменты поток режет ядро, а вот где начинается и
кончается каждый кадр, решает программа.

```text
+----------------------------------------------+
| TCP: поток байт                              |
| +------------------------------------------+ |
| | обёртка кодека                           | |
| |   identity   кадр как есть               | |
| |   padding    [uint16 N][N байт][кадр]    | |
| |   irc        строка PRIVMSG и Base64     | |
| | +--------------------------------------+ | |
| | | кадр: заголовок и payload            | | |
| | | +----------------------------------+ | | |
| | | | payload = IPv4-пакет как есть    | | | |
| | | | +------------------------------+ | | | |
| | | | |      ICMP, TCP или UDP       | | | | |
| | | | +------------------------------+ | | | |
| | | +----------------------------------+ | | |
| | +--------------------------------------+ | |
| +------------------------------------------+ |
+----------------------------------------------+
```

Снимать слои нужно строго в обратном порядке. Если по ошибке записать в TUN
заголовок кадра вместе с IPv4, ядро молча выбросит такой пакет, и понять, в чём
дело, будет непросто.

Заголовок кадра занимает 6 байт.

```text
+--------+--------+----------------+---------+
| magic0 | magic1 | length (uint32)| payload |
| 1      | 1      | 4              | N       |
+--------+--------+----------------+---------+
```

Magic равен `0xAB 0xCD`. В поле length хранится длина payload, `MAX_FRAME_SIZE`
ограничивает её 65536 байтами.

### Потоки

Потоков три: два передают данные, третий печатает статистику. Очередь между ними
не нужна: в каждом направлении работает ровно один поток, который сам читает
данные и сам же их отправляет. Третий поток читает и печатает глобальные счётчики.

| Поток | Функция      | Что делает                            |
| ----- | ------------ | ------------------------------------- |
| A     | pump_out     | read из TUN, pack_frame, encode, send |
| B     | pump_in      | recv, decode, pop_frame, write в TUN  |
| C     | report_stats | раз в 5 секунд печатает tx и rx       |

Очередей и мьютексов нет. Поток A только читает из TUN и только
пишет в сокет, поток B делает наоборот. Функция `make_codecs` создаёт два
экземпляра одного плагина: `enc` достаётся потоку A, `dec` - потоку B.

Перед записью в TUN программа смотрит на первый байт payload. Значение `0x45`
означает IPv4 с заголовком 20 байт без опций, и только такие пакеты попадают в
интерфейс.

Счётчики `tx_packets` и `tx_bytes` меняет только поток A, `rx_packets` и
`rx_bytes` - только поток B, а поток C их лишь читает.

```text
 поток A, наружу            поток B, внутрь            поток С
 ---------------------      ---------------------      ---------------
 read(TUN)                  recv(TCP)                  report_stats
    |                          |
    v                          v
 pack_frame                 decode
    |                          |
    v                          v
 encode                     pop_frame
    |                          |
    v                          v
 send(TCP)                  write(TUN)

 TUN:   поток A только читает, поток B только пишет
 сокет: поток A только пишет,  поток B только читает
 кодек: два объекта, enc у потока A и dec у потока B
```

Почему объектов кодека два, а не один? Кодек хранит состояние: у padding это
буфер и текущий шаг автомата, у IRC - счётчик `seq` и недособранные фрагменты.
Если бы оба потока работали с одним объектом, эти данные перемешались бы.

### Ограничения реализации

- Сервер обслуживает только одного клиента: после `accept` слушающий сокет
  закрывается.
- Обработчика SIGINT нет. Флаг `running` сбрасывается только при ошибке чтения
  или записи и при обрыве соединения. Переподключаться клиент не умеет.
- `running` и счётчики - обычные глобальные переменные, без `std::atomic`. Поток
  C читает счётчики в тот момент, когда A и B их меняют, а по модели памяти C++
  это гонка данных. На стенде числа выглядят правильно, но гарантий здесь нет.
- Если `read`, `send` или `recv` вернули `n < 0`, цикл просто повторяет вызов.
  Отдельной проверки `errno == EINTR` нет, так что настоящая ошибка сокета тоже
  зациклит программу.
- Проверка `payload[0] == 0x45` отсекает IPv4 с опциями: у таких пакетов длина
  заголовка больше 5, и первый байт равен `0x46` или больше.
- Отдельного теста на битый magic у padding нет. Этот случай проверяется в
  парсере кадра (`frame.bad_magic`) и при разборе чужих строк в IRC.

## Направления развития

Вот что можно доделать в этом же коде, не меняя стек:

- короткое рукопожатие с именем плагина, чтобы несовпадение `--plugin`
  обнаруживалось сразу;
- `std::atomic` для флага остановки и счётчиков;
- обработчик SIGINT, который аккуратно закрывает сокет и TUN;
- повтор `read`, `send` и `recv` только при `EINTR`;
- несколько попыток переподключения клиента;
- вынос одного из кодеков в `.so` с загрузкой через `dlopen`.

## Схема стенда

Клиент запускается в отдельном сетевом пространстве имён `wsc`. Если оставить
оба TUN в одном пространстве, ядро сочтёт оба адреса туннеля своими: пакет к
`10.0.0.1` уйдёт через `lo`, а `ping` будет отвечать, хотя программа не прочитает
ни одного байта. Всё дело в том, что таблица `local` просматривается раньше
обычных маршрутов. Проверить это легко: `ip route get 10.0.0.1` покажет `dev lo`.

```text
netns wsc, клиент             хост, сервер
+-------------------------+   +-------------------------+
| ping                    |   | NAT --> интернет        |
|            |            |   |            ^            |
|            v            |   |            |            |
| TUN ws1  10.0.0.2/24    |   | TUN ws0  10.0.0.1/24    |
|            |            |   |            ^            |
|            v            |   |            |            |
| waystation client       |   | waystation server       |
|            |            |   |            ^            |
|            v            |   |            |            |
| veth-c  10.200.0.2/24   |   | veth-h  10.200.0.1/24   |
+------------+------------+   +------------+------------+
             |                             ^
             +--------- TCP 9000 ----------+
```

Скрипт `lab_up.sh` создаёт пространство `wsc` и пару veth, а также назначает
транспортные адреса: `10.200.0.1` на хосте и `10.200.0.2` внутри `wsc`.
Интерфейсы TUN программа создаёт сама: у сервера это `ws0` с адресом
`10.0.0.1/24`, у клиента - `ws1` с адресом `10.0.0.2/24`.

## Путь пакета

На приёме всё повторяется в обратную сторону: кодек снимает обёртку, парсер
отдаёт готовый кадр, и в TUN записывается только IPv4-пакет из payload.

```text
 наружу, поток A                         внутрь, поток B

 read TUN                                write TUN
    |                                       ^
    v                                       |
 pack_frame                              pop_frame
    |                                       ^
    v                                       |
 encode                                  decode
    |                                       ^
    v                                       |
 send TCP ------------ TCP ------------> recv TCP
```

В журнал программа пишет размер полезной нагрузки, то есть длину IPv4-пакета. У
обычного `ping` это 84 байта; заголовок кадра и обёртка кодека сюда не входят.

## Зависимости и сборка

Понадобятся `g++` с поддержкой C++17, CMake, утилита `ip` из пакета iproute2 и
`iptables`. Заголовки `<linux/if.h>` и `<linux/if_tun.h>` входят в заголовки
ядра Linux (пакет `linux-libc-dev`).

Сборка из корня проекта:

```bash
cmake -S . -B build && cmake --build build
```

На выходе получатся `build/waystation` и `build/waystation_tests`.

## Права

Программе нужен доступ к `/dev/net/tun` и право вызывать `ip addr` и `ip link`.
На стенде проще всего запускать всё через `sudo`: он всё равно понадобится для
`ip netns` и `iptables`.

Проверить, что устройство на месте, можно так:

```bash
ls -l /dev/net/tun
```

Это должно быть символьное устройство. Если файла нет, значит, не загружен
модуль ядра, и поможет `sudo modprobe tun`.

Имя интерфейса и адрес проверяются до того, как попасть в команду `ip`. Функция
`plain_token` пропускает только буквы, цифры, точку, слэш, `_` и `-`, так что
подсунуть шеллу лишнюю команду через аргумент не получится.

## Запуск на стенде, уровень 1

Понадобятся три терминала. Сервер нужно запустить первым: клиент подключается
сразу при старте, и если его никто не ждёт, `connect` завершится ошибкой.

Сначала поднимите стенд:

```bash
sudo ./lab_up.sh
```

Затем запустите сервер на хосте:

```bash
sudo ./build/waystation --mode server --port 9000 \
    --tun ws0 --addr 10.0.0.1/24 --plugin padding
```

Теперь клиент внутри `wsc`. Обратите внимание: в `--host` указывается
транспортный адрес сервера `10.200.0.1`, а не адрес туннеля.

```bash
sudo ip netns exec wsc ./build/waystation --mode client \
    --host 10.200.0.1 --port 9000 \
    --tun ws1 --addr 10.0.0.2/24 --plugin padding
```

Проверьте маршрут и запустите ping. `ip route get` должен показать интерфейс
`ws1`:

```bash
sudo ip netns exec wsc ip route get 10.0.0.1
sudo ip netns exec wsc ping -c 3 10.0.0.1
```

После этого остановите оба процесса и запустите их заново с `--plugin irc` -
одинаково на сервере и на клиенте. Ping должен пройти так же.

По каждому пакету программа пишет строку в журнал, а раз в пять секунд поток
статистики выводит сводку:

```text
sent 84 bytes, tx_packets=1
wrote 84 bytes, rx_packets=1
tx 1 packets / 84 bytes, rx 1 packets / 84 bytes
```

`identity` оставлен для отладки TUN и TCP без всяких преобразований, а для
приёмки хватает `padding` и `irc`.

## Выход в интернет, уровень 2

К этому моменту стенд поднят, а сервер и клиент запущены. Внешний интерфейс
скрипт определит сам через `ip route get 8.8.8.8` и запомнит в
`/run/waystation_nat_ext`.

```bash
sudo ./nat_up.sh
sudo ip netns exec wsc ping -c 3 8.8.8.8
```

Вот что делает `nat_up.sh`:

- включает `net.ipv4.ip_forward`;
- выставляет на `ws0` параметр `send_redirects=0`, чтобы хост не отправлял
  клиенту ICMP redirect в обход туннеля;
- добавляет `MASQUERADE` для адресов `10.0.0.0/24`, уходящих через внешний
  интерфейс;
- разрешает `FORWARD` из `ws0` наружу и обратный трафик в состоянии
  `RELATED,ESTABLISHED`;
- ставит внутри `wsc` маршрут по умолчанию `via 10.0.0.1`.

Маршрут по умолчанию меняется только внутри `wsc`, таблицу маршрутов хоста
скрипт не трогает. `MASQUERADE` нужен потому, что адрес `10.0.0.2` за пределами
машины никому не известен. Ядро подменяет адрес отправителя на адрес внешнего
интерфейса хоста, ответы приходят на хост и уже оттуда уходят в туннель.

DNS в `wsc` не настроен, поэтому проверять связь нужно по IP. Если крупные
пакеты не проходят, уменьшите MTU туннеля на клиенте:

```bash
sudo ip netns exec wsc ip link set ws1 mtu 1400
```

## Откат

Сначала остановите оба процесса `waystation` (Ctrl+C). Потом снимите NAT. Это
нужно сделать, пока `wsc` ещё существует, потому что `nat_down.sh` удаляет
маршрут по умолчанию внутри этого пространства. И только после этого разбирайте
стенд:

```bash
sudo ./nat_down.sh
sudo ./lab_down.sh
```

`nat_down.sh` удаляет ровно те правила iptables, которые добавил `nat_up.sh`, и
стирает файл `/run/waystation_nat_ext`. `lab_down.sh` удаляет пространство `wsc`
и интерфейс `veth-h`.

TUN, созданный программой, исчезает сам, как только закрывается последний
дескриптор `/dev/net/tun`, поэтому удалять `ws0` и `ws1` через `ip link delete`
не нужно. TUN клиента к тому же пропадает вместе с пространством имён.

## Параметры командной строки

Если ключ неизвестен, у ключа нет значения или указан неверный режим, программа
печатает `Wrong usage` и завершается с ошибкой.

| Ключ     | Обязателен | Значение                                          |
| -------- | ---------- | ------------------------------------------------- |
| --mode   | да         | client или server                                 |
| --host   | у клиента  | IPv4 сервера на транспорте, на стенде 10.200.0.1  |
| --port   | да         | порт TCP, число от 1 до 65535                     |
| --tun    | да         | имя интерфейса: ws0 у сервера, ws1 у клиента      |
| --addr   | да         | адрес и маска, например 10.0.0.1/24               |
| --plugin | да         | identity, padding или irc                         |

Сервер слушает `0.0.0.0` на заданном порту и принимает одно соединение. На
сокете включён `SO_REUSEADDR`: после обрыва порт ещё какое-то время считается
занятым, а с этой опцией сервер можно сразу перезапустить на том же 9000.

## Протоколы на проводе

### Кадр

Заголовок кадра занимает 6 байт, за ним идёт сырой IPv4-пакет. `recv` может
вернуть что угодно: половину заголовка, один кадр, два кадра сразу или кадр
вместе с началом следующего. Поэтому парсер копит байты и отдаёт кадр только
тогда, когда их набралось столько, сколько указано в заголовке.

### Padding

Перед кадром записана длина паддинга, а за ней идут сами случайные байты. `N`
выбирается случайно от 0 до 64 (`PAD_MIN` и `PAD_MAX`) и хранится как `uint16`
старшим байтом вперёд.

```text
+----------+------------------+------+
| uint16 N | N случайных байт | кадр |
+----------+------------------+------+
```

Длина стоит в начале не случайно. TCP - это поток, и у сообщения в нём нет
«последних» байт. Формат «кадр, потом паддинг, в конце длина» разобрать нельзя:
чтобы прочитать `N`, нужно знать, где кончается паддинг, а чтобы это узнать,
нужно уже знать `N`. Когда длина идёт первой, на каждом шаге понятно, сколько
байт ждать дальше.

Декодер устроен как автомат с тремя состояниями. Состояние сохраняется между
вызовами `decode`, потому что `recv` приносит данные кусками любого размера.
Паддинг затрагивает только обёртку, байты IPv4 внутри кадра остаются прежними.

```text
 PAD_WAIT_N -- прочитаны 2 байта N --> PAD_WAIT_PAD
      ^                                           |
      |                                           | пропущены N байт
      |                                           v
      +----------- кадр ------------ PAD_WAIT_FRAME
```

В состоянии `PAD_WAIT_N` декодер ждёт два байта длины, в `PAD_WAIT_PAD`
пропускает `N` байт паддинга, а в `PAD_WAIT_FRAME` собирает кадр по его
заголовку и передаёт парсеру.

### IRC

Это не настоящий IRC-клиент, а только имитация того, как выглядит трафик. Команд
`NICK`, `USER`, `JOIN`, `PING`/`PONG` нет, таймаута на потерянный фрагмент тоже.

Кадр сначала кодируется в Base64: в payload могут встретиться байты `0x0D` и
`0x0A`, а строка IRC как раз заканчивается на `\r\n`. Результат режется на куски
по `IRC_B64_CHUNK` (400 символов), и каждый кусок уходит отдельной строкой:

```text
PRIVMSG #tunnel :FT:<seq>:<frag>/<total>:<base64>\r\n
```

Здесь `seq` - номер кадра, `frag` - номер фрагмента начиная с 1, а `total` -
сколько всего фрагментов в кадре. Строка, в которой за `IRC_LINE_MAX` (8192)
символов так и не встретилось `\r\n`, отбрасывается, а чужие строки
пропускаются. Если в нумерации фрагментов появилась дыра или пришёл другой
`seq`, недособранный кадр выбрасывается. Когда все фрагменты одного `seq`
собраны по порядку, Base64 декодируется обратно в кадр.

Вот как один и тот же ping выглядит на проводе с разными кодеками:

```text
 identity   [ magic | length | IPv4 ]
 padding    [ N | случайные байты | magic | length | IPv4 ]
 irc        [ PRIVMSG #tunnel :FT:..:base64(кадр) \r\n ]
```
